# gym_tracker_engine — Audit Report

_Generated by 5-angle multi-agent audit (2026-08-26). Each item cites file:line evidence from direct code reads._

## Open decisions needing user input

- **Programs tab / `ProgramTemplate` CRUD / `FocusRun` / `startRun` mechanism** currently has zero effect on what the engine actually trains. Decide: delete the tab and its old-tree dependency chain entirely, or rebuild it against the engine's own domain (`specializationBlocks`/`sessionOrchestration`)? This also determines the fate of the AI Assistant's `adjust_exercise_params` tool (retire vs. rebuild).
- **Dead `src/components/stats/StatsTab.tsx` and `src/components/calendar/ProgramCalendarView.tsx` (+ `excelCalendarExport.ts`)** are confirmed orphaned (superseded by `engine/StatsTab.tsx` and `engine/CalendarTab.tsx`), but the engine replacements are missing exactly the features these dead files implement (monthly bar chart; per-session exercise detail, header stats, Excel export). Decide: mine the dead files for that logic before deleting, or accept the current engine tabs as intentionally scoped-down and delete the dead files outright.
- **Dead `src/components/session/` subtree** (`SessionPlanPanel`, `SessionExerciseCardList`, `SessionExerciseDetailsModal`, `sessionPlanUtils`) is confirmed safe to delete per an existing regression test, but it's also the only place the Max-value display, "how max is calculated" explanation, progression-cycle fraction, Done/Left counters, and per-side/dumbbell weight formatting still exist in this codebase. Decide: port that logic into the new `ExerciseDetailModal.tsx` first, or accept the simplification and delete as-is.
- **`weighIns`/`circumferenceMeasurements`** have a type and persisted-state slot but no reducer case and no UI anywhere. Decide: build out the logging UI + reducer case, or delete the dead schema fields before they complicate a future IndexedDB migration.
- **The "autonomous" part of the "autonomous adaptive training engine"** — auto focus-muscle rotation (`pickNextFocus`/`buildFocusHistorySeed`), the ACWR safety ceiling/deload trigger (`exceedsCeiling`/`shouldDeload`), and auto-correction after missed sessions (`autoCorrection.ts`) — is fully implemented, tested, and documented but never called from any live code path. Decide when/whether this ships, since it's currently misrepresented as done in design docs.
- **"Show progression insights" toggle** has no equivalent in the engine tabs (history chips are now always-on). Confirm this is an intentional simplification rather than a regression to fix.

## Findings

### [CRITICAL] Engine-tree IndexedDB writes are fire-and-forget — real data loss risk on every save, and "Reset All Data" cannot be trusted to actually clear the engine DB
- **Category:** data-risk
- **Location:** `src/components/engine/EngineStateProvider.tsx:41-45`; `src/infrastructure/storage/indexedDbRepository.ts:37-40`; `src/App.tsx:165-180` (`handleResetAllData`)
- **Evidence:**
```tsx
useEffect(() => {
    if (!loaded) return
    repository.saveState(state)
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [state, loaded])
```
`repository.saveState` is `async` and can reject (quota exceeded, DB blocked, IndexedDB unavailable). The call is neither `await`ed nor `.catch()`ed, and it fires on every engine-tree dispatch (`SET_PROFILE`, `CREATE_GOAL`, `LOG_WORKOUT`, `CONFIRM_SESSION_INPUTS`, `END_GOAL`, `REPLACE_STATE`).
- **Impact:** React state updates in memory synchronously, so the UI shows a logged workout / new goal / saved profile as successful regardless of whether the IndexedDB write actually succeeded. A rejected promise is an unhandled rejection visible only in devtools; nothing is shown to the user. On next load, `loadState()` returns the last *successfully* persisted blob, silently reverting the most recent change(s). The same unguarded call underlies `handleResetAllData` — if that particular write fails, the UI still claims "Autonomous-engine data erased too" while the old profile/goals/logs are still in IndexedDB and will reappear on next load.
- **Recommendation:** Await the save and surface failures to the user (persistent "save failed, data not backed up" banner + retry) instead of a bare fire-and-forget call.

### [HIGH] `saveAppState` (OLD tree/localStorage) has no error handling, and the app's only crash-recovery UI discards whatever change triggered the failure
- **Category:** data-risk
- **Location:** `src/data/storage.ts:252-258` (`saveAppState`); `src/App.tsx:107-109` (save effect); `src/main.tsx:16-44` (`RootErrorBoundary`)
- **Evidence:** `saveAppState` calls `localStorage.setItem(STORAGE_KEY, JSON.stringify(payload))` with no `try/catch`, running synchronously in a `useEffect` on every old-tree state change. `localStorage.setItem` throws synchronously on quota exceeded. `RootErrorBoundary` catches render-phase errors app-wide but only renders "Сталась несподівана помилка. Оновіть сторінку." with a reload button.
- **Impact:** If `setItem` throws (e.g. large accumulated `workoutLogs`/`programTemplates` pushing past localStorage quota), the exception propagates, React unmounts to the full-screen "reload" prompt. Reloading re-runs `loadAppState()` from the last successful write, permanently discarding the change that caused the crash — with no message that data was lost or why.
- **Recommendation:** Wrap `localStorage.setItem` in try/catch inside `saveAppState`, surface a specific "couldn't save — storage full" message, and avoid pushing the user toward an unconditional reload when the real cause is an unsaved write.

### [HIGH] Data tab's backup/export functions never include engine-tree data; the only real backup for that data lives in a different, unadvertised tab
- **Category:** parity-gap / data-risk
- **Location:** `src/App.tsx:288-318` (`handleExportState`, `handleExportCleanState`); `src/data/storage.ts:264-315` (`exportAppStateJson`, `exportCleanAppStateJson`, typed strictly to `AppState`); `src/App.tsx:720-753` (Data tab UI copy); working engine-tree backup exists only at `SetupTab.tsx:59-91,178-190`

The Data tab's copy never mentions this exclusion. A working engine-tree export/import exists only inside the "Автопрофіль" tab's Backup card, which itself discloses: *"Separate from the app's main State Backup on the Data tab — this covers only Setup/Today data."*

A user who follows the Data tab's guidance and downloads a "Full Backup" believing it protects their training data will lose all real goals/workout history/weigh-ins/profile on site-data clear, reinstall, or device switch — that data was never in the downloaded file. The only real safeguard is a card easy to miss on an unrelated tab.

### [MEDIUM] Engine-state load path has no error handling — an IndexedDB open/read failure leaves every engine tab stuck on "Loading…" forever with no diagnostic
- **Category:** data-risk
- **Location:** `src/components/engine/EngineStateProvider.tsx:26-39`
- **Evidence:**
```tsx
useEffect(() => {
    let cancelled = false
    repository.loadState().then((loadedState) => {
      if (cancelled) return
      if (loadedState) {
        dispatch({ type: 'REPLACE_STATE', state: loadedState })
      }
      setLoaded(true)
    })
    return () => { cancelled = true }
  }, [])
```
No `.catch()`; `setLoaded(true)` only runs inside `.then()`.
- **Impact:** If `repository.loadState()` rejects (blocked upgrade, disabled storage, environment restriction), `setLoaded` never fires. Every engine-driven tab renders "Loading…" indefinitely, with no error and no way to distinguish "empty profile" from "load failed and could be retried."
- **Recommendation:** Add `.catch()` that sets an error state distinct from "loaded with empty data," and surface it in the UI.

### [CRITICAL] AIAssistant's `adjust_exercise_params` tool is inert or actively misleading — it targets a field no engine component reads, and typically has no valid target to act on at all
- **Category:** logic-bug / parity-gap
- **Location:** `src/domain/reducer.ts:597-616` (`setExerciseParamOverride`, writes only OLD-tree `focusRuns[].weightOverrides/setsOverrides/repsOverrides`); `src/components/AIAssistant.tsx:229-232` (`handleConfirmApply` dispatches this, keyed by `runId`); `src/services/aiContext.ts:61-67` (the only place these override fields are ever read — back into the AI's own prompt); grep of `src/components/engine/*` for `weightOverrides` — zero matches in `TodayTab.tsx`, `FinishSessionTab.tsx`, `FocusTab.tsx`, `HomeTab.tsx`; `src/data/storage.ts:221-232` (`createInitialState()` sets `focusRuns: []`); repo-wide grep for `dispatch({ type: 'startRun'` returns zero matches in any component.
- **Evidence:** The tool's entire effect is a patch to `FocusRun.weightOverrides`, a field no live engine-tab component ever reads (exhaustive grep), and there is no in-app UI path left that creates a `FocusRun`. Two concrete failure modes: (1) a fresh-install user has `focusRuns: []` forever — `runId` is a required tool parameter with no valid value, and if the model hallucinates one, `handleConfirmApply`'s `.map` finds no matching run so the dispatch is a total no-op while the UI still tells the user "вагу → Xkg змінено" (silent false success); (2) because `gym_tracker` and `gym_tracker_engine` share the identical `localStorage` key `'training-os-app-state'`, a user who previously used the OLD app on the same browser has stale OLD-app `focusRuns` carried into the NEW app's OLD tree — the tool then silently mutates that stale, invisible run with no Runs-list UI anywhere in the new app to observe the effect.
- **Impact:** The AI's "I adjusted your weight" confirmation is either a complete no-op reported as success, or a mutation of stale cross-app data invisible to the user in either failure mode.
- **Recommendation:** Retire the tool/feature for the engine build (remove `adjust_exercise_params` and its confirm-card UI) unless the Programs/FocusRun disconnect below is resolved by rebuilding it against the engine's own domain (point `aiContext.ts` at `PersistedState`, give the model a tool that actually affects `sessionPrescription`/`assembleTodaysSession` inputs).

### [HIGH] `mostRecentTopSet` is unscoped by specialization block, so a second goal cycle on a previously-trained exercise can be born already "complete"
- **Category:** logic-bug
- **Location:** `src/application/sessionPrescription.ts:32-47` (`mostRecentTopSet`); `src/application/goalStatus.ts:18-29` (`checkGoalNeedsRenewal`); `src/components/engine/TodayTab.tsx:70-71`; `src/components/engine/FinishSessionTab.tsx:81-82`; `src/application/goalCreation.ts:25-48`; `src/application/goalRecommendation.ts:51-58`; `src/application/oldAppHistory.ts:22-46`; `src/components/engine/SetupTab.tsx:239-244`
- **Evidence:** `mostRecentTopSet` scans **every** `WorkoutLog` regardless of specialization block (no `block.startedAt` filter). Both `TodayTab.tsx:70` and `FinishSessionTab.tsx:81` feed its result into `checkGoalNeedsRenewal`, which fires `'targetMet'` the instant `currentWeightKg >= goal.targetWeightKg` — with no check the log came from the current block. Meanwhile a new goal's `startingWeightKg` is seeded from a *different* source entirely — `suggestStartingWeightFromOldApp(oldWorkoutLogs, exerciseId)`, a lookup into the OLD app's separate state tree — with `targetWeightKg = startingWeightKg + weeklyRate*durationWeeks`.
- **Impact:** Concrete sequence: user runs a bench-press block through the engine, progresses to 80kg (logged), block ends. Weeks later they start a new bench-press goal; Setup auto-suggests a stale starting weight (e.g. 55kg) from old-app history and a target of ~60kg. The instant the goal is created, `mostRecentTopSet` finds the old 80kg top set from the *previous, unrelated* block, `checkGoalNeedsRenewal` returns `'targetMet'` before a single rep is logged, and both "План сесії" and "Завершити" immediately show the renewal screen — the user cannot plan or log a single session for the new goal. The same unscoped lookup also feeds `prescribeExercise`'s APRE branch: the freshly-chosen `goal.startingWeightKg` is silently ignored whenever any prior log exists for the exercise.
- **Recommendation:** Scope `mostRecentTopSet` (or add a block-scoped variant) to logs with `completedAt >= block.startedAt` when evaluating the active block's goal/renewal status and prescribing today's weight.

### [HIGH] The "autonomous" layer — auto focus-rotation, ACWR safety ceiling/deload trigger, and auto-correction — is fully built, tested, and documented, but nothing in the application layer ever calls it

### [MEDIUM] Workout dates are bucketed by UTC calendar day but compared against local "now", shifting which ACWR window/day a session lands in
- **Category:** logic-bug
- **Location:** `src/application/muscleLoadHistory.ts:23` (`log.completedAt.slice(0, 10)`); `src/domain/acwr/acwr.ts:19-20` (`daysBefore`); `src/application/sessionCadence.ts:62`; `src/components/engine/FinishSessionTab.tsx:136` (`completedAt: new Date().toISOString()`); `src/components/engine/StatsTab.tsx:57` (`const asOf = new Date()`)
- **Evidence:** A workout is timestamped as an absolute UTC instant (`toISOString()`), then bucketed into a calendar day via `.slice(0, 10)` on that UTC string. `acwr.ts:19-20`'s `daysBefore` parses that UTC-date string (parsed as UTC midnight) and diffs it against `asOf.getTime()`, an absolute instant from plain `new Date()`.
- **Impact:** For any user behind UTC, a workout logged in the evening local time crosses into the next UTC calendar date, shifting which 7-day/28-day window a session counts in near a boundary (skewing `acwr()`/`classifyAcwrZone`), can flip `daysSinceLastLoad`/`isDetrainingRisk` (14-day threshold) a day early or late, and makes the Calendar tab show a `✓` on the wrong local day for evening sessions.
- **Recommendation:** Derive the bucketing date from the user's local calendar day at logging time (capture a local `YYYY-MM-DD` alongside `completedAt`, or bucket using local-time components), and make `daysBefore`/window comparisons consistent about UTC vs. local.
